# Pull-request scenarios

Each directory is one pull request used by the golden tests of the diff engine and every later
phase (change model, impact, risk, context).

```
<scenario>/
  scenario.yaml        description, refs, provider placeholders, expected files
  base/                full base tree (plain files)
  patch.diff           the pull request as a git-style unified diff (text only)
  expected/            golden outputs, one file per phase
```

`auth-bypass` encodes PRD §151 (see `docs/planning/tasks/P09-P14-diff-change-impact-risk-semantic-context.md` §0.3).
`diff-edge-cases` is generated by `engine/crates/diff-engine/tests/golden_edge_cases.rs`
(binary and multi-MiB content is not committed) and only holds its golden dispositions.

## How the trees are built

The Rust tests never call `git`. `diff_engine::testkit::Scenario::load(name)` reads `base/`,
applies `patch.diff` with a strict in-process applier (every context and removed line must
match) and commits both trees with a fixed identity and timestamp, so the SHAs are the same on
every machine. Downstream crates use it through the `testkit` feature of `diff-engine`.

`fixtures/build.sh --pr <name>` builds the same two commits with git into
`fixtures/.build/prs/<name>` and writes the `git diff --histogram -U3` and
`--name-status -M50%` references; `--update-expected` copies them into `expected/`. The
`expected/git-diff-u3.patch` files are the parity references for the hunk tests.

## Updating a golden

Golden JSON is canonical (sorted keys, no SHAs). When a test reports a mismatch it prints the
full actual JSON. Review the change, then either copy it into the golden file or rerun the test
with `REVIEWGRAPH_BLESS=1` to rewrite it:

```
REVIEWGRAPH_BLESS=1 cargo test -p diff-engine --test golden_auth_bypass
```

A pull request that changes a golden must explain the semantic change in its description.
Fixture content is synthetic; `fixture_tree_has_no_forbidden_strings` rejects credential-like
strings anywhere under this directory.
