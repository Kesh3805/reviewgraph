### E2E-001 — MVP acceptance test
Status: ☐

- **Task ID:** E2E-001
- **Title:** MVP acceptance test: signed webhook -> fake GitHub API -> checkout from a local bare repo -> index -> review (replay) -> verify -> publish, with one trace
- **Problem:** Each stage has unit and integration tests, but nothing proves the assembled system meets the MVP exit criteria. Without a closed-loop test, regressions between the NestJS control plane, the queue, the Rust worker and publication go unnoticed.
- **Why it exists:** Master plan §8 (M6 exit), §11 (end-to-end level), §16 (MVP exit criteria 1 to 7), risk R8 (no API keys or GitHub App in dev, so a fake provider and the replay model are required). It is the last task on the critical path.
- **Scope:**
  - A docker compose test profile that runs api, worker, engine, postgres, redis, qdrant and openobserve.
  - A fake GitHub API server (Node) that serves the endpoints the product calls and records every request.
  - A scenario driver (TypeScript, Jest) that sends a correctly signed webhook and asserts outcomes.
  - Fixture repository and recorded replay responses for the auth-bypass pull request.
- **Explicit non-scope:** Real GitHub or real model calls (E2E-002), performance targets (PERF), UI tests (WEB), load testing.
- **Files/modules expected to change:** `infra/compose/docker-compose.test.yml` (profile `e2e`), root `package.json` (`test:e2e`), `.github` or CI workflow definition (CI-007 job).
- **New files/modules expected:**
  - `tests/e2e/{package.json,jest.config.ts,setup.ts}`
  - `tests/e2e/fake-github/{server.ts,routes.ts,recorder.ts}`
  - `tests/e2e/specs/{mvp-happy-path.spec.ts,duplicate-delivery.spec.ts,superseded-head.spec.ts}`
  - `tests/e2e/support/{signing.ts,openobserve.ts,db.ts,fixtures.ts}`
  - `fixtures/pull-requests/auth-bypass/` (base and head commits, replay JSON)
- **Dependencies (task IDs):** GH-002, GH-009, SUP-001, SUP-003, API-007, PIPE-003, PIPE-009, PIPE-010, PIPE-011, GW-005, FND-008, OBS-003, OBS-004, DEV-001.
- **Implementation details:**
  - Test GitHub App credentials (an RSA key, webhook secret) are generated by `setup.ts` for each run and passed to containers by environment; they are test-only values and are never real credentials.
  - The fake server implements: installation token (`POST /app/installations/:id/access_tokens`), `GET /repos/:o/:r/pulls/:n`, the pull request files list, the create-review `POST .../reviews`, list review comments, check runs create and update, list existing PR comments, and the clone-credentials-related repository metadata. Its clone URL points at a `file://` local bare repository mounted into the worker (the worker is started with `ALLOW_FILE_REMOTES=1` for this profile only). Every request is appended to a recorder with method, path, headers and body. Any request to an unmodelled route (including any merge route) fails the test.
  - Happy-path steps: build the fixture repo and index the base commit through a `repository-index` job; send a webhook `pull_request.opened` with a valid `X-Hub-Signature-256` and a unique `X-GitHub-Delivery`; wait (poll the database, 90 s limit) for the run to reach `COMPLETED`.
  - Assertions on the recorded review payload: exactly one `POST .../reviews`; `event == "COMMENT"`; `commit_id` equals the head SHA; the comments array has exactly the expected inline findings (path, line, side, marker with run id) and no suppressed trap findings; the body contains the summary with coverage and tools-not-executed lines; the check run conclusion is `neutral`; no request contains `APPROVE`, `REQUEST_CHANGES` or a merge route.
  - Database assertions: all candidates have a lifecycle state, suppressed ones have reasons, `published_findings` rows carry comment ids from the fake server, only changed files were reparsed (counter), the snapshot written for the head is a delta.
  - **Single trace:** query OpenObserve's search API with retry (ingestion delay up to 30 s) for all spans of the run's `trace_id` taken from the webhook span; assert one trace id covers services `api` and `review-worker` and contains the span names `webhook_received`, `job_enqueue`, `repository_checkout`, `incremental_graph_update`, `impact_analysis`, `context_selection`, `reviewer_execution`, `model_request`, `finding_verification`, `deduplication`, `publication`.
  - `duplicate-delivery.spec.ts`: the same delivery id twice yields one run and one review. `superseded-head.spec.ts`: a second head arrives mid-run; the fake server receives no review for the first head.
- **Data model changes:** None.
- **API/protocol changes:** None. The compose profile and a test-only environment contract are added.
- **Concurrency semantics:** Scenarios run sequentially, each in a fresh database (`pnpm dev:reset`-style truncate) so runs cannot interfere.
- **Failure behavior:** On failure the driver dumps the recorder, run state, and worker logs (redacted) into the CI artifacts; it never prints source or tokens.
- **Idempotency considerations:** The duplicate-delivery scenario covers webhook, queue and publish idempotency end to end.
- **Security considerations:** The fake server rejects unauthenticated requests (installation token required); signing uses constant-time comparison paths of the real endpoint, and a negative scenario sends a bad signature and expects 401 and no run.
- **Observability additions:** None new; this task consumes spans and metrics. It asserts `publish_outcomes_total` and the absence of dead jobs.
- **Tests required:**
  - `mvp_happy_path_publishes_expected_review`
  - `bad_signature_rejected_and_no_run_created`
  - `duplicate_delivery_publishes_once`
  - `superseded_head_publishes_nothing_for_old_head`
  - `entire_run_is_one_trace_in_openobserve`
  - `unmodelled_github_route_fails_the_test`
  - `no_dead_jobs_after_scenarios`
- **Benchmarks if applicable:** Webhook-to-published latency under replay is recorded (not gated) and stored as a CI artifact for PERF-008.
- **Acceptance criteria:** `pnpm test:e2e` passes locally and in the CI nightly and release jobs; MVP exit criteria 1 to 7 each map to at least one assertion (a table in the spec header).
- **Definition of done:** Global DoD, plus `docs/operations/e2e.md` explains running, debugging and re-recording replay fixtures.

### E2E-002 — Live smoke procedure
Status: ☐

- **Task ID:** E2E-002
- **Title:** Live smoke procedure: real GitHub App and real model key, a manual gate documented in `docs/operations`
- **Problem:** E2E-001 uses a fake GitHub and a replay model, so it cannot detect real API drift, real permission gaps, real webhook delivery, or real model behavior. A human-run procedure is needed before the first release, and it cannot be automated in CI because it needs secrets, a public ingress and cost.
- **Why it exists:** Master plan §8 (M6 exit: "E2E-002 run manually against a real repository with a real App and model key"), §16 MVP exit criteria, and audit §6 items 5 and 6 (no public ingress, no model keys in the current environment). It is also the proof that the App permissions are minimal and that no merge capability exists.
- **Scope:**
  - `docs/operations/live-smoke.md`: prerequisites, step-by-step procedure, expected results, cost cap, teardown.
  - `scripts/live-smoke/preflight.sh` (and `.ps1`): checks that required environment variables are set and non-empty without printing them, that the tunnel is reachable, and that the model key works with a one-token call.
  - A report template `docs/operations/live-smoke-reports/TEMPLATE.md` and a release-gate check `scripts/live-smoke/check-report.sh` that fails unless a report for the release candidate exists and is signed off.
- **Explicit non-scope:** Automating the run in CI, creating the GitHub App or any account on the user's behalf, storing secrets in the repository, load or performance testing.
- **Files/modules expected to change:** `docs/operations/README.md` (index), release checklist doc if CI-009 defines one.
- **New files/modules expected:**
  - `docs/operations/live-smoke.md`
  - `docs/operations/live-smoke-reports/TEMPLATE.md`
  - `scripts/live-smoke/{preflight.sh,preflight.ps1,check-report.sh}`
- **Dependencies (task IDs):** E2E-001, GH-001, GH-002, GH-010, DEV-001, DEV-003, OBS-007, CI-009.
- **Implementation details:**
  - **Prerequisites (human, outside the repository):** a disposable private test repository containing the fixture project; a GitHub App created from the manifest in `docs/operations/github-app.md` with exactly the permissions `contents: read`, `pull_requests: write`, `checks: write`, `metadata: read` and subscribed to the pull request events; the App installed on the test repository only; a public tunnel (for example ngrok) to the local API; an Anthropic or OpenAI key provisioned with a spend cap; the stack running through `pnpm dev:up`. All secrets are supplied through a local untracked `.env.live` and never committed.
  - **Procedure:** (1) run preflight; (2) open a pull request that reproduces the auth-bypass scenario; (3) observe the webhook delivery in the App's delivery log (200 or 202); (4) wait for the review; (5) verify the checklist below; (6) push a second commit and confirm supersession and no duplicate comments; (7) close the pull request; (8) revoke the key and uninstall the App from the test repository.
  - **Checklist mapped to MVP exit criteria 1 to 7:** webhook verified; only changed files reparsed (worker log counter); impact and context selected within budget; correctness and security reviewers ran; the expected finding is posted inline at the correct line with a summary; no APPROVE or merge action appeared on the pull request; the full run is one trace in OpenObserve (attach the trace id); token usage and cost recorded and under the cap; check run state correct.
  - **Pass criteria:** every checklist item ticked, no secret visible in logs (the procedure includes a grep of captured logs for the key prefixes), cost under the cap stated in the report, and the report signed with date, commit SHA tested and the person's name.
  - The report template records: image digests, versions (`verification_version`, prompt versions), provider and model, tokens, cost, latency, trace id, deviations and follow-up task IDs.
  - `check-report.sh <commit>` verifies a report file exists for that release commit (or a descendant within 30 days with no engine changes) and has every box ticked.
- **Data model changes:** None.
- **API/protocol changes:** None.
- **Concurrency semantics:** One operator at a time per test repository.
- **Failure behavior:** A failed step produces a defect task before the gate can be signed; the report records the failure rather than editing history.
- **Idempotency considerations:** The procedure is repeatable; each run uses a new branch and pull request.
- **Security considerations:** Disposable repository only; spend-capped key; the preflight script never echoes secret values (it prints `set` or `missing`); logs are scrubbed before attaching; the App is uninstalled afterwards. Confirms the permission list is minimal (no contents write, hence no merge ability).
- **Observability additions:** The report links the OpenObserve trace and the review dashboard (OBS-007).
- **Tests required:**
  - `preflight_reports_missing_variables_without_printing_values` (script test in `scripts/live-smoke/tests`)
  - `preflight_fails_on_unreachable_tunnel`
  - `check_report_fails_when_report_absent`
  - `check_report_fails_when_unticked_box_present`
  - `check_report_passes_for_signed_report`
- **Benchmarks if applicable:** The report captures end-to-end latency for the small pull request as an input to PERF-008 (target under 60 s).
- **Acceptance criteria:** A signed live-smoke report exists for the MVP release candidate and `check-report.sh` passes; this is a required item on the release checklist.
- **Definition of done:** The procedure was executed once by someone other than its author, the doc was corrected from that run, and the signed report is committed.

### INV-001 — No full rebuild in PR review
Status: ☐

- **Task ID:** INV-001
- **Title:** Invariant 1 (PRD §147): PR review never requires a complete graph rebuild under normal operation
- **Problem:** A review that silently re-indexes the whole repository would reproduce the legacy latency (15 to 21 minutes) and defeat the incremental design.
- **Why it exists:** PRD §147 Invariant 1, PRD §141 (incremental update acceptance), ADR-004.
- **Scope:** An executable test that proves the PR review path performs only an incremental update when a base snapshot exists, and that the missing-base case is handled explicitly rather than by a hidden rebuild.
- **Explicit non-scope:** Correctness of the incremental algorithm (INC-012 oracle test), index performance (PERF-005).
- **Files/modules expected to change:** `docs/architecture/invariants.md` (index entry).
- **New files/modules expected:**
  - `engine/crates/invariants/tests/inv_001_no_full_rebuild.rs` (the test lives in the dev-only `invariants` crate so it can see `pipeline`, `incremental` and `codegraph` together; the crate has no library code and `publish = false`)
  - `engine/crates/invariants/Cargo.toml`
- **Dependencies (task IDs):** PIPE-003, INC-009, INC-012, IDX-001, FND-008.
- **Implementation details:**
  - Test location: `engine/crates/invariants/tests/inv_001_no_full_rebuild.rs`. Fixture: a repository of at least 200 files with a full base snapshot, and a PR that edits 2 files.
  - Assert through counters (`graph_full_rebuilds_total`, `files_reparsed_total`, `files_skipped_unchanged_total`) that the review run performs zero full rebuilds, reparses exactly the changed files, and writes a `delta` snapshot.
  - Missing base snapshot case: the pipeline enqueues a `repository-index` job and the run waits or fails transiently with reason `base_snapshot_missing`; the test asserts `graph_full_rebuilds_total{trigger="pr_review"} = 0`.
  - Static guard: a source scan asserts the `pipeline` PR-review module does not reference the full-index entry point (`FullIndexer::run`), listing the only allowed caller (`repository-index` handler).
- **Data model changes:** None.
- **API/protocol changes:** None.
- **Concurrency semantics:** Single run; deterministic.
- **Failure behavior:** The test fails if any rebuild counter is non-zero or the snapshot kind is `full`.
- **Idempotency considerations:** Re-running the review is also asserted to produce no rebuild.
- **Security considerations:** None.
- **Observability additions:** Requires the counter `graph_full_rebuilds_total{trigger}` to exist (added by INC tasks); the test fails if it is missing, so the metric cannot be removed unnoticed.
- **Tests required:**
  - `inv_001_pr_review_does_not_rebuild_graph`
  - `inv_001_changed_files_only_are_reparsed`
  - `inv_001_missing_base_snapshot_does_not_trigger_inline_rebuild`
  - `inv_001_pr_path_has_no_reference_to_full_indexer`
- **Benchmarks if applicable:** None.
- **Acceptance criteria:** `engine/scripts/cargo.sh test -p invariants inv_001` passes and is listed as required in CI.
- **Definition of done:** Global DoD, plus the test name and path appear in the invariant index `docs/architecture/invariants.md`.

### INV-003 — Every published finding is anchored
Status: ☐

- **Task ID:** INV-003
- **Title:** Invariant 3 (PRD §147): every published finding is anchored to changed behavior or impact created by the PR
- **Problem:** A model can comment on unrelated code. Publishing it teaches users to ignore the tool and violates the "changed behavior" promise.
- **Why it exists:** PRD §147 Invariant 3, PRD §141 (changed-code anchor in every published finding), ADR-011 stage 2.
- **Scope:** A test that every finding that survives to `PUBLISHED` has an anchor that is either inside a changed hunk or reachable by a recorded path from a changed symbol in the impact graph, and that findings without such an anchor are suppressed.
- **Explicit non-scope:** The anchor stage implementation (VER-004).
- **Files/modules expected to change:** `docs/architecture/invariants.md`.
- **New files/modules expected:**
  - `engine/crates/invariants/tests/inv_003_findings_anchored.rs`
  - `fixtures/pull-requests/unanchored-claims/` (PR plus replay output with in-hunk, impact-path and unrelated-file claims)
- **Dependencies (task IDs):** VER-004, VER-010, IMP-008, PIPE-003, FND-008.
- **Implementation details:**
  - Fixture replay produces four candidates: (a) inside a changed hunk, (b) in an unchanged caller reachable from a changed symbol within the impact budget, (c) in an unchanged, unrelated file, (d) in an unchanged region of a changed file with no path to any change.
  - Assert: (a) and (b) are published or reach `PRIORITIZED`, with an anchor class recorded (`InHunk`, `ImpactPath`) and, for (b), a stored path; (c) and (d) end `SUPPRESSED_NOT_ACTIONABLE` with gate `anchor`.
  - Property test: for any generated set of candidates and diffs, every finding in `PUBLISHED` or `PRIORITIZED` has a non-null `anchor_class` and (when class is `ImpactPath`) a path whose first node is a changed symbol; the test runs 500 cases.
  - A database invariant query (also used in E2E-001) selects published findings lacking an anchor class or path and must return zero rows.
- **Data model changes:** None (uses VER tables).
- **API/protocol changes:** None.
- **Concurrency semantics:** None.
- **Failure behavior:** The test fails if any unanchored finding reaches a publishable state.
- **Idempotency considerations:** Not applicable.
- **Security considerations:** None.
- **Observability additions:** Requires `findings_suppressed_total{reason}` with a distinct `anchor` gate label.
- **Tests required:**
  - `inv_003_in_hunk_finding_is_anchored_and_publishable`
  - `inv_003_impact_path_finding_records_path_from_changed_symbol`
  - `inv_003_unrelated_file_finding_suppressed`
  - `inv_003_unchanged_region_without_path_suppressed`
  - `inv_003_property_published_implies_anchor`
  - `inv_003_db_query_finds_no_unanchored_published_rows`
- **Benchmarks if applicable:** None.
- **Acceptance criteria:** All tests pass; the property test seed is logged and reproducible.
- **Definition of done:** Global DoD, plus the index entry.

### INV-005 — Consumer-specific rules never in generic graph semantics
Status: ☐

- **Task ID:** INV-005
- **Title:** Invariant 5 (PRD §147): consumer-specific rules cannot become generic graph semantics
- **Problem:** Embedding one repository's conventions, module names or framework quirks in the graph or analyzer core makes the product a one-customer tool and corrupts results for everyone else.
- **Why it exists:** PRD §147 Invariant 5, master plan principle 8 (generic core, specific edges), target-architecture §2.1 ("NestJS and repository-specific knowledge never appears in `codegraph`").
- **Scope:** Guard tests over the generic crates: kind enums, source tokens, and the location of rule packs.
- **Explicit non-scope:** The reference profile and rule pack itself (POL-007), framework adapters (NEST tasks).
- **Files/modules expected to change:** `docs/architecture/invariants.md`.
- **New files/modules expected:**
  - `engine/crates/invariants/tests/inv_005_no_consumer_rules_in_core.rs`
  - `engine/crates/invariants/denylist/consumer-terms.txt`
  - `engine/crates/invariants/snapshots/graph_kinds.snap` (insta)
- **Dependencies (task IDs):** CG-001, CG-002, POL-007, TSA-009.
- **Implementation details:**
  - **Kind snapshot:** an `insta` snapshot of the exact `NodeKind` and `EdgeKind` lists (PRD §17 and §18 plus `Repository`). Adding a kind requires updating the snapshot, which forces a reviewer to see it; the test header says new kinds must be generic (justified by two independent consumers) and states the review rule.
  - **Term denylist:** `denylist/consumer-terms.txt` has one case-insensitive term per line, with initial contents taken from the reference consumer's repository name, product names and module path prefixes as recorded in POL-007. The test scans `src/` of `codegraph`, `analysis-ir`, `incremental`, `graph-storage`, `diff-engine`, `impact`, `context-engine`, `verification` and fails on any hit. ### HIST-004 — Anti-reinforcement rules (PRD §69)
Status: ☐

- **Task ID:** HIST-004
- **Title:** Enforce anti-reinforcement: no historical signal becomes policy without repetition, evidence, acceptance or configuration (post-MVP)
- **Problem:** PRD §69 forbids "one bad review -> stored as policy -> repeated forever". Without structural guards, history-derived behavior (HIST-003) could amplify a single reviewer's mistake, suppress legitimate findings after one dismissal, or entrench a biased pattern.
- **Why it exists:** PRD §69, §68 ("signals, not rules"), §144 (precision bias), target-architecture §3.10 precedence (explicit policy > documented architecture > inferred > generic).
- **Scope:**
  - A `SignalAdmission` gate that every history-derived signal, convention or suppression must pass before influencing review: repetition, supporting repository evidence, explicit acceptance, or human-configured policy.
  - Limits on influence: caps on weight, decay, a diversity requirement, a conflict rule against current repository evidence, and expiry/review of auto-derived suppressions.
  - An audit trail and an operator "explain" command showing why a signal was admitted or rejected.
- **Explicit non-scope:** Computing signals (HIST-003); outcome tracking (HIST-002); human-authored rules (POL-*, which bypass the gate by definition).
- **Files/modules expected to change:** `engine/crates/profile/src/history/signals.rs` (route all emissions through the gate), `engine/crates/verification/src/suppression.rs` (history-derived suppression must carry admission evidence), `engine/crates/profile/src/precedence.rs` (history never outranks explicit policy).
- **New files/modules expected:** `engine/crates/profile/src/history/admission.rs`, `engine/migrations/{seq}_signal_admissions.sql`, `engine/apps/review-cli/src/commands/history_explain.rs`, `docs/reviewers/anti-reinforcement.md`.
- **Dependencies:** HIST-002, HIST-003, POL-004, POL-006, VER-011.
- **Implementation details:**
  - Admission rule (all required unless noted): (1) repetition: >= 5 independent observations over >= 3 distinct PRs and >= 2 distinct hashed authors/reviewers within the window; (2) repository evidence: the pattern is corroborated by the graph or code (e.g. the convention holds in >= 90% of >= 10 samples, per target-architecture §3.10); (3) one of: explicit human acceptance (`useful` feedback, a maintainer-applied label, or inclusion in `.review/config.yaml`) or a human-configured policy. A signal with only (1) and (2) may influence ranking at reduced weight (<= 0.05) but can never suppress or create findings.
  - Single-source guard: observations originating from one reviewer's comments, one PR, or one ReviewGraph finding cannot satisfy repetition; ReviewGraph's own past findings are not independent evidence of correctness (prevents self-reinforcement loops).
  - Suppression from dismissals: a dismissal suppresses only the exact fingerprint (existing POL-006 behavior); pattern-level suppression needs the full admission and expires in 90 days unless re-confirmed.
  - Conflict rule: if current repository evidence contradicts the signal (e.g. the pattern is now violated by a majority), the signal is demoted automatically and flagged.
  - Every admitted or rejected signal has an `admission_decisions` row with reasons; `review history explain <signal_id>` prints them.
  - A kill switch `history.enabled=false` disables all history influence instantly.
- **Data model changes:** `signal_admissions(signal_id, organization_id, decision admitted|rejected|demoted, reasons jsonb, evidence_summary jsonb, decided_at, expires_at)` with RLS.
- **API/protocol changes:** CLI `review history explain`; internal endpoint `GET /internal/signals/:id/admission`.
- **Concurrency semantics:** Admission evaluated inside the signal refresh transaction (HIST-003); decisions are versioned and immutable, the latest wins.
- **Failure behavior:** Fail closed: if admission evidence is missing or evaluation errors, the signal is not admitted and the review proceeds without it.
- **Idempotency considerations:** Same inputs produce the same decision; re-evaluation does not duplicate rows (unique on `(signal_id, input_hash)`).
- **Security considerations:** Prevents poisoning by a single malicious or mistaken contributor (a documented threat); explanations contain counts and IDs only; tenant RLS.
- **Observability additions:** Counters `history_signals_admitted_total`, `history_signals_rejected_total{reason}`, `history_signals_demoted_total`; span event `signal_admission`.
- **Tests required:**
  - `single_review_never_creates_policy`
  - `single_author_repetition_is_insufficient`
  - `reviewgraph_own_findings_not_independent_evidence`
  - `unaccepted_signal_cannot_suppress_or_create_findings`
  - `contradicting_repository_evidence_demotes_signal`
  - `pattern_suppression_expires_after_90_days`
  - `history_never_outranks_explicit_policy`
  - `admission_fails_closed_on_error`
  - `kill_switch_disables_all_history_influence`
- **Benchmarks if applicable:** None.
- **Acceptance criteria:** A scripted adversarial history (one reviewer rejecting a pattern 20 times in one PR; ReviewGraph findings repeated 10 times) admits zero suppressing signals; a legitimately repeated and accepted pattern across >= 3 PRs and 2 reviewers is admitted; benchmark corpus metrics with history enabled never exceed the QB-003 regression thresholds.
